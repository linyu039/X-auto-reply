# X 评论 AI 自动回复

一个 Chrome MV3 扩展：点开 X（Twitter）任意一条评论的回复框，它会自动读上下文 → 调大模型生成回复 → 模拟人工逐字敲进输入框 → **填好就停住**，你自己按「回复」。想回下一条，再亲手点开另一条。

## 安装

1. Chrome 打开 `chrome://extensions/`
2. 右上角打开「开发者模式」
3. 点「加载已解压的扩展程序」，选中本目录 
4. 建议把扩展图标固定到工具栏

## 配置

点扩展图标，填三样东西：

| 项 | 说明 |
|---|---|
| API Base | OpenAI 兼容地址。DeepSeek: `https://api.deepseek.com/v1`；OpenAI: `https://api.openai.com/v1`；本地 vLLM/Ollama: `http://127.0.0.1:11434/v1` |
| API Key | 对应服务的密钥 |
| 模型名 | 如 `deepseek-chat`、`gpt-4o-mini`、`qwen-plus` |
| 视觉模型名 | 带图时自动切过去，默认 `deepseek-flash`，不用改 |

点「测试接口」会先发一条示例请求，验证凭平和模型是否通。

回复风格在同页「人设」「硬性规则」里改。默认规则已经去掉了营销腔、话题标签、"感谢分享"这类空话，并强制语言跟随对方（英文评论用英文回）。

## 风格预设

设置页「回复策略」最上面有个下拉，选一个就把人设、规则、长度、温度整段换掉，点「保存配置」生效。改过的地方照样能再手改，预设只是起点。

| 预设 | 适合 | 长度 | 温度 |
|---|---|---|---|
| 出摊交友（隐晦回关） | 想让人回来关注，但不能直说"互关" | 15–40 字 | 1.05 |
| 交友搭话（贴吧味） | 想在评论区认识人、找话搭子 | 15–45 字 | 1.0 |
| 嘴臭抬杠（贴吧味） | 抬杠好玩、戳破吹牛 | 10–40 字 | 1.1 |
| 温和接话（默认） | 正常参与讨论 | 1–2 句 | 0.95 |

### 出摊：怎么让人回关又不被压流量

平台对"互关、回关、互粉、互fo、关注我、求关注、follow back、f4f"这类词是直接打 spam 标的，写了轻则限流重则折叠。但圈里人彼此都懂行话，所以改成隐喻说：

| 类型 | 说法 | 对方怎么懂 |
|---|---|---|
| 浇水 | 互浇、浇一下、水给你浇上了 | "关注"的谐音变形，圈内通行 |
| 串门 | 常来串门、认个门、门牌我记下了 | 串门 = 去你主页逛逛 |
| 摊位 | 摊在主页、这摊儿不散、路过就坐、给你留个座 | 摊 = 主页，坐下 = 关注 |
| 蹲守 | 我在你主页蹲着、每天来打个卡、老地方见 | 长期待在你主页 = 常驻关注 |

规矩是**一句只能放一个**。连着说两个以上，机器也许认不出，但人一眼看出你在拉粉，反而掉价。

配套还限了三条：不要说"交个朋友""很高兴认识你"这种直白搭讪；不要夸不要捧（摊主不会对客人肉麻）；必须先接住对方那条里的具体内容，再顺带招呼一声——没有内容打底，光剩招呼就是硬广。

交友那套的逻辑是：**不喊口号，靠具体话题熟起来**。

- 必须从对方这条里抓一个具体的东西接——一个数字、一个地点、一个物件、一个时间、一个观点，不许泛泛而谈
- 结尾留钩子：一句具体的追问，或"我也…你呢"，让对方有话可接
- 允许"老哥/姐妹/同款/蹲一个/这个我懂"，但每条最多用一个
- 明令禁止"很高兴认识你""交个朋友吧""互关吗""求带"——这类直球搭讪一看就是机器人
- 禁止查户口（"你是做什么的""哪里人""多大了"）

嘴臭那套限定在**只怼说法，不怼人**：明确写死不骂脏话、不碰家人/地域/长相，避免把账号玩废。

要加自己的风格：改 `presets.js` 里加一个 key 就行，结构照抄，`name/persona/rules/maxLen/temperature/maxTokens/samples` 这几项。

## 识别推文配图

推文里如果有图，可以让模型一起看，这样回复能接梗图、表情包、截图的点。

**打开方式**：扩展设置 → 模型接口 → 勾「识别推文配图」。

**它会自己换模型。** 上面填的是文本模型，下面「视觉模型名」填看图用的那个。带图的时候自动切过去，不带图还用文本模型——省得让贵模型写所有文案。

### DeepSeek 怎么配

DeepSeek 的多模态模型是 `deepseek-flash`（V4.1 Flash），base_url 和 key 跟 `deepseek-chat` 完全一样，只换模型名：

| 项 | 值 |
|---|---|
| API Base | `https://api.deepseek.com/v1` |
| 模型名（写文字） | `deepseek-chat` |
| 视觉模型名（看图） | `deepseek-flash` |

v1.7.0 起「视觉模型名」默认就填好了 `deepseek-flash`，勾上「识别推文配图」直接能用。旧的 `deepseek-v4-flash-vision-exp` 已被官方退役，请求会转发到最新的 Flash 模型。

### 其它服务的视觉模型

| 服务 | 模型名 |
|---|---|
| OpenAI | `gpt-4o`、`gpt-4o-mini` |
| 阿里通义 | `qwen-vl-max`、`qwen2.5-vl-72b-instruct` |
| 智谱 | `glm-4v`、`glm-4v-plus` |
| Google | `gemini-2.5-flash`、`gemini-2.5-pro` |
| 月之暗面 | `moonshot-v1-8k-vision-preview` |

**取图规则**

- 只认推文正文里配的图（`pbs.twimg.com/media`），头像和 emoji 一律跳过
- 缩略图 URL 自动升级成 `name=large` 原图
- 一次最多 4 张
- 同时取「你要回复的那条」和「主推文」的图，去重后合并

**自动降级**：如果视觉模型不吃图（返回 400 且报错提到 image/vision/multimodal），会自动退回文本模型、去掉图片重发一次，不会因此整条失败。所以填错名字也不会炸，只是看不到图。

图片是以 URL 形式传给模型的，服务端需要能访问 `pbs.twimg.com`。国内部分服务商可能拉不到，这种情况回复会退化成只看文字。DeepSeek 官方接口拉得到。

## 使用

两种用法，任选：

### 方式一：跟随模式（推荐，默认开启）

直接在 X 上正常刷推，看见想回的评论就点它的「回复」按钮。

弹窗一打开，插件立刻开始工作：读取这条评论 + 主推文上下文 → 调模型生成 → 逐字敲进输入框 → **停住不动**。

```
跟随 → @alice_cn: 静音红轴打字声音是小了，但段落感真的没了…
⌨ 已填入 27 字：段落感确实是个取舍，我现在靠换键帽把手感找回来了一点。
◐ 已填好，停在输入框 —— 你确认后点「回复」，插件不会自己发
```

然后你自己：

- 觉得可以 → 按「回复」发出去
- 觉得要改 → 直接改，光标已经停在末尾
- 觉得不行 → 全选删掉，自己写

插件**不会**自动发送，**不会**跳到下一条，**不会**关掉弹窗。它填完就撒手。

要回下一条评论，**再手动点开那条的「回复」**，重复上面的过程。一条一条来，节奏完全由你掌控。

想让它在填完后直接发出去：扩展设置里勾「填完自动发送」。默认不勾。

插件不会抢你已经打过的字——如果弹窗打开时输入框里已经有内容，它直接退出。

关掉跟随：点面板上的「跟随模式 · 开（只填不发）」按钮，变成「关」。

### 方式二：单步模式（手动一条一条来）

1. 在 X 上打开一条推文的详情页（URL 含 `/status/...`）
2. 页面右下角出现「AI 评论回复」小面板
3. 点「回下一条」

**点一次只处理一条，做完就停**，绝不会自己往下跑。日志最后会打出「单步完成 —— 要再回一条，再点一次「回下一条」」。想回下一条，再点一次按钮。

单步模式下「停止」按钮只在你想中断当前这一条时用得上。

### 方式三：连续模式（默认开启）

面板上按钮显示「开始连续」，点一次就一条接一条往下回，**回满「本次条数上限」条（默认 8）自动停**，不会无限跑下去。

想改成一条一条手动控制：扩展设置 → 跟随模式 → 取消勾选「循环模式」。

每条之间按「最小/最大间隔」等待（快速档默认 11–28 秒）。**如果你觉得「AI 跟不上」或者「太快了」，把这两个间隔调大，或者把「本次上限」改小。**

### 下滑加载更多

评论区快到底时，插件会自动往下滑，把新评论加载出来再继续回。这一版的下滑做了三件事：

1. 派发真实的 `wheel` 事件 —— X 的虚拟列表认这个，光改滚动位置有时不触发加载
2. 一次滑 1.2 屏（原来 0.9 屏，容易在同一批内容里打转）
3. 同时对比 `document.scrollingElement.scrollHeight` 有没有变长，而不只是看滚没滚

日志会写明每次下滑的结果：

```
⤓ 下滑 · 页面变长 2400px，新评论在加载
⤓ 下滑 · 到 8420px（暂时没有新内容）
⤓ 已经滚不动了（到底）
```

连续 12 次下滑都没有新内容，才会判定「真的到底了」并停止。如果日志里反复出现「暂时没有新内容」，说明这个帖子的评论确实被 X 折叠了（作者限制回复，或评论区已被平台收敛），这时候换一条推文。

三种方式的关系：跟随模式和单步/循环模式互斥运行（同一时刻只有一个在动），跟随模式优先级更高。

### 三种运行模式

| 模式 | 勾选项 | 行为 |
|---|---|---|
| 全自动 | 什么都不勾（`autoSend` 默认开） | 生成 + 填入 + 发送 |
| 人工确认 | 取消「自动发送」 | 只把回复填进输入框并停下，你自己点发送 |
| 纯预演 | 勾上「预演模式」 | 只调模型生成，不碰页面 DOM，适合先看回复质量 |

第一次用强烈建议先跑「纯预演」看十几条输出，确认语气对了再放开。

## 自动点赞

回复完顺手给这条评论点个赞。默认**关**，面板上「点赞 · 关」点一下开，popup 里也有开关。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `autoLike` | false | 回复完给这条评论点赞 |
| `likeMain` | false | 主推文也一起赞 |
| `maxLikes` | 40 | 每次运行最多赞多少个 |

三个细节：

- **已经赞过的不会重复点。** X 把未赞和已赞做成两个不同的按钮（`data-testid="like"` / `"unlike"`），所以看一眼按钮在不在就知道点没点过，不用猜。
- **点赞失败不影响回复。** 点完按钮没变化（被限流、网络慢）只记一行日志，主流程继续。
- **主推文赞一次就够。** 循环模式下同一篇推文会被回复很多条评论，但主推文只会被赞一次，第二次开始自动跳过。

想手动补赞某一条，控制台里：

```js
// 赞主推文
window.__XAR__.like()
// 赞指定某条（articles 里按顺序取）
window.__XAR__.like(document.querySelectorAll('article[data-testid="tweet"]')[2])
// 返回 'ok' / 'already' / 'gone' / 'fail'
```

点赞是**通知对方**的动作，比回复更容易被看到，也不占 280 字额度。所以在「出摊」那套里，点赞比回复更稳妥：回复容易说错话，点赞不会。

## 自动回关

评论发出去之后，顺手关注这条评论的作者。默认**关**，面板上的「关注 · 关」点一下开。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `autoFollow` | false | 评论发出去后关注评论作者 |
| `maxFollows` | 50 | 本次最多关注多少个 |
| `followCooldownMin` | 15 | 撞到限流后等几分钟再接着关注 |

### 怎么找到关注按钮的

X 的评论卡片里**没有**关注按钮，按钮藏在用户名片（hover card）里。所以流程是：

```
找到这条评论的用户名链接
  → 派发 mouseover（带真实坐标，X 要坐标才弹名片）
  → 等 0.8–1.4 秒
  → 抓到 [data-testid="HoverCard"]
  → 里面找文字是 Follow / 关注 的按钮
  → 点
```

如果那条推文本身带内联的关注按钮（时间线里的推荐推文会有），就跳过名片直接点。

### 已关注的怎么判断

按钮文字就是状态：

| 按钮文字 | 状态 | 处理 |
|---|---|---|
| `Follow` / `关注` | 没关注 | 点它 |
| `Following` / `正在关注` | 已关注 | **直接跳过，不重复点** |
| `互相关注` | 互关 | 跳过 |

另外本地存了一份 `followedHandles`（上限 2000），关注过的 handle 记在里面，下次遇到同一个人的评论连名片都不用弹。

### 撞到关注限制怎么办

X 对关注频次有硬限制，撞到了会弹一条 toast：

```
You are unable to follow more people at this time.
```

插件认这条提示（也包括中文的「操作过于频繁」「稍后再试」等），然后：

1. **不停止运行**，回复照常继续往下跑
2. 把当前这个人塞进待关注队列
3. 记一个冷却时间（默认 15 分钟），面板按钮变黄字「关注 · 冷却中」
4. 冷却到期后，下次运行时会先把队列里的人补上，日志打「➕ 限制解除，补关注 @xxx」

这就是「出现限制不用管，等解除继续」的实现方式：不打断主流程，排队等。

### 量的参考

单账号一天关注 100–200 个是安全区间，超过很容易触发限制甚至被临时锁功能。所以：

- `maxFollows` 默认 50，别拉到几百
- 关注和回复共用同一条评论，跑 15 条回复最多关注 15 个，不会失控
- 真被限制了别反复重试，等冷却就行，硬刷会延长惩罚时间

### 手动补关注

控制台里：

```js
// 关注页面上第一条评论的作者
window.__XAR__.follow(document.querySelectorAll('article[data-testid="tweet"]')[1])
// 返回 'ok' / 'already' / 'gone' / 'nocard' / 'nobtn' / 'limit'
```

## 速度调节

四档，面板上点「速度 · xxx」按钮循环切换，popup 里也有下拉，改完**立即生效**，不用刷新页面。

| 档位 | 系数 | 每两条之间的等待 | 输入速度 |
|---|---|---|---|
| 极速 turbo | 0.12 | 约 4–9 秒 | 几乎瞬间 |
| 快速 fast（默认） | 0.38 | 约 11–28 秒 | 很快 |
| 标准 normal | 1.0 | 约 30–75 秒 | 拟人 |
| 保守 safe | 2.2 | 约 66–165 秒 | 很慢，最像手打 |

系数缩放的是「所有等待环节」：开弹窗后的停顿、逐字符输入的间隔、点发送前的停顿、两条之间的间隔。**不改**回复内容、条数上限、跳过规则。

想更快就直接改 `content.js` 里的 `SPEED_MAP`，甚至加自己的一档：

```js
const SPEED_MAP = { insane: 0.05, turbo: 0.12, fast: 0.38, normal: 1, safe: 2.2 };
const SPEED_LABEL = { insane: '变态', turbo: '极速', fast: '快速', normal: '标准', safe: '保守' };
const SPEED_ORDER = ['insane', 'turbo', 'fast', 'normal', 'safe'];
```

## 自己改配置

popup 面板最下面有「高级（原始配置）」区块，是一段可以直接编辑的完整 JSON。里面列出**全部**可调字段，改完点「保存配置」就生效，不用动代码。

能改的东西包括：

- 表单里已有的每一项（`apiBase` / `model` / `persona` / `rules` / `minDelay` / `maxLen` …）
- 表单里没有的字段，比如 `speed`、`maxTokens`
- `customSelectors` —— **X 改版导致插件失效时，不用改代码，在这里覆盖选择器就行**：

```json
{
  "sendBtn": "button[data-testid=\"tweetButton\"]",
  "editor": "div[data-testid^=\"tweetTextarea_\"]",
  "replyBtn": "button[data-testid=\"reply\"]"
}
```

可覆盖的键（对应 `content.js` 顶部的 `SEL` 对象）：
`tweet` `text` `userName` `replyBtn` `editor` `sendBtn` `dialog` `closeBtn` `profileLink` `promote`

JSON 写错的话，点保存会直接报「JSON 语法错误」并指出位置，不会把配置写坏。

## 直接改源码

整个扩展没有任何构建步骤，改完 `content.js` 存盘，去 `chrome://extensions/` 点扩展卡片上的刷新箭头，再刷新 X 页面即可。想调更细的东西：

| 想改什么 | 改哪里 |
|---|---|
| 哪个更快/更慢 | `content.js` 的 `SPEED_MAP` |
| 等待间隔的具体数值 | `content.js` 里所有 `srand(a, b)`，数字是毫秒 |
| 页面元素选择器 | `content.js` 顶部 `SEL` 对象，或 popup 的 `customSelectors` |
| 和模型说话的方式 | `background.js` 的 `buildMessages()` |
| 回复去格式化的规则 | `background.js` 的 `cleanReply()` |
| 判定发送成功的标准 | `content.js` 的 `confirmSent()` |
| 判定输入是否成功 | `content.js` 的 `inputAccepted()` |

## 防风控设计

- 两条之间随机等待，间隔随速度档缩放（默认 11–28 秒）
- 每小时上限、本次条数上限双重限制
- 输入是逐字符 `insertText` 敲进去的，不是一次性 `innerHTML` 赋值，DraftJS 的 `beforeinput` 会被正常触发
- 跳过自己的评论、推广推文、可选跳过蓝V账号
- 已回复的推文 ID 持久化在 `chrome.storage.local`，重开页面不会重复回
- 同一批回复内容会作为上下文喂回模型，让它避开刚才用过的句式

## 工作原理

```
content.js                     background.js
──────────                     ─────────────
扫 article[data-testid=tweet]
  → 取 status id / 文本 / handle
  → 去重、过滤推广与本人
  → XAR_GENERATE ────────────→ /chat/completions
  ←──────────── 回复正文
点 button[data-testid=reply]
  → 等 div[data-testid=tweetTextarea_0]
  → 分块 insertText
  → 点 button[data-testid=tweetButton]
  → 弹窗消失 = 成功
```

DOM 选择器集中在 `content.js` 顶部的 `SEL` 常量里。X 改版导致「回复框未出现」时，只需要改那一个对象，逻辑不用动。

## 输入内容怎么保证不被污染

X 的编辑器是 DraftJS，程序化写入有几种坑，插件逐层挡掉：

1. **空态占位符**：「发布你的回复」是编辑器内部的占位符节点，光标落进去的话字会写偏，看着有字其实没提交。
   `placeCaretAtEnd()` 会绕开占位符，把光标放在最后一个真实文本节点末尾。
2. **激活编辑器**：先插一个**零宽字符**（U+200B）再删掉，逼编辑器脱离空态。用零宽而不是字母，因为万一删除失败，零宽字符看不见、不占字数。
3. **清空必须清到 0 字**：`clearEditor()` 最多做 3 轮逐字删除，还清不掉就全选删除兜底。清完再检查一次，不为 0 就再清一遍。
4. **严格比对**：写入后读回来的文本必须和目标**完全一致**（去掉空白和零宽字符后）。宽松比对会把「a回复正文」当成成功。
5. **残留前缀识别**：`extraPrefix()` 发现正文前面挂了东西（典型的就是 `a`、`aa`），会清空重填一次；重填还对不上就跳过这条，**不发半截内容**。

对应测试 `test/run-sticky.mjs`：先往编辑器里塞 `aa` 再让插件填，断言 `aa` 被清掉、连跑 3 条发出去的内容都不带前缀垃圾。

## 输入框被灌爆怎么办

X 的编辑器在某些时序下会把刚插进去的内容**再渲染几遍**，连续模式跑几轮就能堆到几千字，字数变成 `-7520` 这种负数，回复按钮永久灰。

插件现在有三道闸：

1. **开工前检查**：`typeInto()` 一开始就看框里有多少字。超过目标的 2 倍会先 `hardClear()` 暴力清空。
2. **边填边查**：每插一个字就比一次字数，超过目标的 1.6 倍立刻判「注入失控」，强行清空、放弃这一条，**不再继续往里灌**。
3. **刹车**：连续 4 条失败自动停整个循环，日志打 `⛔ 连续 4 条失败，自动停下`。

`hardClear()` 用 Range 框住编辑器内容再删（不用 `selectAll`，焦点跑飞时会选中整页），最多试 5 轮，最后手段是直接清空 `[data-contents]` 并派发 `input` 事件唤醒 React。

另外回复长度硬上限是 **400 字**（`Math.min(cfg.maxLen, 400)`）。配置里把最大长度写成 5000 也不会真的灌 5000 字进去。

对应测试 `test/run-flood.mjs`：mock 打开「放大 3 倍」开关复现这个问题，验证插件能在 39 字时就抓住、清空、不发；关掉开关后恢复正常；框里预置 680 字垃圾也能清掉再填。

**框里已经有几千字垃圾、插件也清不掉时**：在输入框里点一下，`Ctrl+A` 全选，`Delete`。清空后插件会自动恢复正常。

## 注入失败（v1.13.3 修的那个）

日志里如果出现过 `✗ 注入失败` / `✗ 没写进 X 的编辑器`，根因是**选错了元素**。

X 的回复框结构是这样：

```html
<div data-testid="tweetTextarea_0">     <!-- 外壳：不吃任何输入 -->
  <div contenteditable="true" role="textbox"></div>   <!-- 真正的编辑器 -->
</div>
```

以前 `SEL.editor` 把外壳排在前面，`querySelector` 一命中就直接把外壳交给了 `execCommand`。在外壳上调 `execCommand('insertText')` 不会报错、不会有任何反应——浏览器只是安静地什么都不做。于是五级注入全部落空，日志报「注入失败」。

现在两层保护：

1. `SEL.editor` 的选择器顺序改为**内层 contenteditable 优先**；
2. 新增 `realEditor(el)`：拿到元素先判 `isContentEditable`，不是就往下找 `[contenteditable="true"]`，还没有就往上找 `closest()`。所有取编辑器的地方（`waitForEditor`、跟随模式、`__XAR__` 调试接口）都过这一层。

注入顺带也重排成了六级，越靠前越稳：

| 级别 | 方式 | 说明 |
|---|---|---|
| ① | 全选覆盖 `insertText` | 选中全部内容后一次性替换，结果必然等于目标文本 |
| ② | CDP `Input.insertText` | 走浏览器真实输入管线，一次提交整段，需要 `debugger` 权限 |
| ③ | 粘贴事件 | 构造 `ClipboardEvent` + `DataTransfer` |
| ④ | 分块 `insertText` | 每块 6–18 字 |
| ⑤ | 逐字符 `insertText` | 每个字间隔 8–24ms，最像真人，但也最容易出碎片 |
| ⑥ | 直改 DOM | 兜底，多半会被 X 丢掉 |

**注意 ⑤ 排在最后**：每敲一个字 X 都可能重排一次，光标一错位，整段就会被叠成 `下雨下天下雨下留…` 那种碎片。只有当上面几级全部无效时才会用到它。

**每次失败都会打一行明细**，形如 `⑤ 逐字符：插了 0/18 个字，框里 0 字｜按钮灰`。看到「插了 0 个字」就是元素选错了；看到「插了 18/18 但按钮灰」就是字数超了或者没权限。

出问题时点面板的 **诊断输入**，它会自动打开回复框、打印编辑器实现（Lexical / DraftJS）、空态占位符、子节点结构，再把六级注入逐个跑一遍，每级给出 `DOM N 字｜aria-disabled=?｜✅生效 / ⚠有字但按钮仍灰 / ✗完全没进去`。跑完点 **复制日志** 一键复制 60 行。

对应测试：`test/mock-x.html` 的编辑器已改成和真站一样的「外壳 + 内层 contenteditable」结构，六个 e2e 全部在这个结构上通过。

## 正文翻倍 / 一直灰（v1.15.0 修的那批）

日志里出现这两种，根因是同一个系列的：

```
⚠ 注入失控：输入框涨到 34 字（目标 17 字），强行清空并放弃这条
… 正文写进去了，但发送按钮是灰的（按钮文字「回复」，已找到按钮）
```

### 一、34 字 / 44 字 = 正好两倍

不是编辑器随机放大，是**同一段文字被插了两遍**。来源有两个：

1. **两个流程同时写**：你在批量模式跑着的时候点开某条评论的回复框，跟随模式也接手同一条，两个流程各插一遍。
2. **清空不可靠**：上一级注入失败后「清空 → 换下一级重插」，但没清干净就插了第二份。

对应的两道锁：

- `typeInto()` 外层加了 `writing` 互斥锁，同一时刻只允许一个流程写同一个框；`runLoop()` 开跑前会等跟随模式写完（`followBusy || writing`）。
- 每一级注入前统一走 `resetEditor()`：最多清 3 轮，**清完必须真的是 0 字**才往下走；清不干净直接放弃这条并提示你手动 `Ctrl+A` + `Delete`。宁可少发一条，也不发两遍。

对应测试 `test/run-double.mjs`：框里预置同样长度的旧内容再写入，断言结果不叠加；两个 `typeInto` 并发，断言最终只有一份。

### 二、发送按钮一直灰

按钮灰有两种情况，现在分开处理：

| 现象 | 含义 | 处理 |
|---|---|---|
| 文字不对 + 按钮灰 | 没写进去 | 换下一级注入方式 |
| 文字完全正确 + 按钮灰 | 写进去了，但 X 的编辑器状态没同步（DOM 有字、React 认为空） | 走兜底：截短 → 真实回车 → 摘掉禁用标记强点 |

根治手段是**让注入走浏览器原生输入管线**：v1.15.0 把 `chrome.debugger` 的 `Input.insertText` 提到**第一级**。它派发的是真实 `beforeinput`，X 的 Lexical 必然会更新内部状态，不会出现「DOM 有字、状态为空」。

前提是**焦点必须在输入框里**，所以新增了 `ensureFocus()`：按 `mousedown → mouseup → click` 真实序列点一次编辑器，再核对 `document.activeElement`，最多重试 6 轮。焦点没落进去时会明确打日志 `… 焦点没落进输入框，注入可能失效`。

注入顺序（越靠前越稳）：

| 级别 | 方式 | 说明 |
|---|---|---|
| ① | CDP `Input.insertText` | 浏览器原生输入，一次提交整段，Lexical 必然收到 |
| ② | 全选覆盖 `insertText` | 选中全部后一次性替换 |
| ③ | 粘贴事件 | 构造 `ClipboardEvent` + `DataTransfer` |
| ④ | 分块 `insertText` | 每块 6–18 字 |
| ⑤ | 逐字符 `insertText` | 最容易出碎片，只有上面全废才用 |
| ⑥ | 直改 DOM | 兜底，多半被 X 丢掉 |

触发 CDP 时浏览器顶部会闪一条「已开始调试此浏览器」的黄条，几秒后自动消失，属正常现象。

## 连续模式跑不动（v1.15.1 修的那个）

单条能发、一开连续就全废，卡在两个地方：

**一、上一轮的回复弹窗没关。** X 的回复框是模态弹窗，它开着的时候再点下一条的「回复」按钮**没有任何反应**。而 `waitForEditor()` 会把**还挂在页面上的旧弹窗**里的编辑器当成本轮的框交出去 —— 于是内容写进了上一条评论的框里，以为成功了，其实全错。

现在每轮开框之前强制收尾：

```js
const liveDialog = () => Array.from(document.querySelectorAll(SEL.dialog)).filter(visible)[0];
for (let i = 0; i < 3; i++) {
  if (!liveDialog()) break;
  log('  · 上一轮的回复框还开着，先关掉再开这条');
  await closeModal();
  await srand(300, 600);
}
if (liveDialog()) await waitUntil(() => !liveDialog(), 2500, 100);
```

**二、上一轮的文字当草稿留着，`execCommand` 删不干净。** 清不掉就换下一级注入，而下一级又往后追加 —— 目标 22 字最后变成 44 字，正好翻倍。

现在清空有一条硬兜底：常规三轮 `hardClear` 之后还有残留，就用**真实键盘事件** `Ctrl+A` → `Backspace`。这条路走浏览器原生输入管线，Lexical 必然收到 `beforeinput`，一定删得掉。

```
… 常规清空失效（还剩 22 字），改用真实 Ctrl+A + Delete
```

看到这行说明兜底生效了，不用管。

连续失败阈值也从 3 条放宽到 4 条，避免偶发抖动把整轮掐掉。

### 失败原因直接写脸上

以前面板只有一个「失败 6」，看不出卡在哪一步。现在每条失败都归了类，面板在统计下面多一行：

```
失败 6 条：回复框没弹出来×4、按钮灰，回车+强点都发不出×2
```

对照表：

| 面板上写的 | 真实含义 | 对症 |
|---|---|---|
| 回复框没弹出来 | 点「回复」后 12 秒没等到编辑器 | 上一条的弹窗没关干净，或这条被限流 |
| 注入的内容对不上 | 写进去的文字和目标不一致 | X 的编辑器在重排，换一条试试 |
| 按钮灰，回车+强点都发不出 | 文字进去了但按钮永远点不动 | 对方设了「只有关注的人能回复」，或账号被限流 |
| 模型接口报错 | API 返回 4xx/5xx | 检查余额、Key、模型名 |
| 模型返回空 | 模型给了空字符串 | 换个模型或调低 temperature |

## 滑不动 / 界面乱跳（v1.16.0 修的那个）

「不自动下滑，划一下又弹回去」不是选择器写错了，是**滚动方式**根本不对。

### 为什么以前的滑法在 X 上无效

| 以前的写法 | 为什么没用 |
|---|---|
| `window.scrollTo(0, y)` | X 时间线是虚拟列表，它在自己的 scroll 回调里把位置算回去，你赋值下一帧就被拉回原处 —— 就是那个「弹回去」 |
| `el.dispatchEvent(new WheelEvent('wheel'))` | JS 造出来的事件 `isTrusted === false`，X 的懒加载监听器直接忽略，一条新评论都不会加载 |
| `scrollIntoView({behavior:'smooth'})` | 平滑滚动是动画，X 在动画途中重排，动画被拦腰打断，停在半路 |

### 现在的做法

走 Chrome DevTools Protocol 的 `Input.dispatchMouseEvent`，`type: 'mouseWheel'`：

```js
await dbgSend(tabId, 'Input.dispatchMouseEvent', {
  type: 'mouseWheel',
  x: Math.round(window.innerWidth * 0.35),   // 落在主列上，避开面板
  y: Math.round(window.innerHeight * 0.5),
  deltaX: 0,
  deltaY: step,
  pointerType: 'mouse'
});
```

这是**浏览器层面真实产生的滚轮**，`isTrusted === true`，走的是和你手动滚鼠标滚轮完全一样的路径。X 分不出区别。

配套的三条修正：

1. **滚不动就换步子再试**，最多三次，步长 1 / 0.6 / 1.4 倍 —— X 偶尔会吞掉第一次滚动。
2. **贴到底就立刻收手**，不再空转 12 次。判据是 `scrollTop + viewH >= scrollHeight - 24`。
3. **滚动之前先关弹窗**。回复弹窗是模态的，它开着的时候页面滚不动，强行滚会把弹窗甩走。

### 「界面自己跳走了」

三个来源，都堵了：

- **`scrollToTweet` 以前每次都用 smooth 滚一遍**。现在目标推文如果已经完整在视口里（上方留 90px 给导航栏、下方留 110px），一个像素都不动。

## 常见问题

**面板不出现**
刷新页面。扩展只对 `x.com` / `twitter.com` 注入；旧标签页需要在扩展装好后重新打开。

**回复框未出现**
X 的 DOM 结构变了。打开 DevTools 看回复框现在的 `data-testid`，更新 `content.js` 里的 `SEL.editor`。

**发送按钮不可点**
分两种情况，日志会分开告诉你：

- **「正文写进去了，但发送按钮是灰的」+ 截短后变亮** → 字数超了。把「回复最大长度」降到 60–120（X 对中日韩字符按 2 倍计权，280 权重 ≈ 140 个汉字）。
- **截多短都灰** → X 的编辑器状态没同步：DOM 里有字，它自己以为空。插件会连试两条路把内容送出去：
  1. **真实回车键**（CDP 派发，不看按钮状态）—— X 网页版回复框是 Enter 发送、Shift+Enter 换行；
  2. **摘掉禁用标记强点** —— X 的按钮是 `div[role="button"]`，点击走 React 的 `onClick`，不完全依赖 `disabled`。

  两条都不成，说明是账号侧的硬限制：对方设了「只有关注的人能回复」、你被对方拉黑、或者账号在限流里。日志会直接写出来。

对应测试 `test/run-grey.mjs`：mock 打开「框里有字但按钮永远灰」的开关，验证插件照样能把内容发出去，统计记为成功，日志点明走了哪条兜底路径；关掉开关后正常路径也不受影响。

**一直说「没有可回复的评论」**
当前视口内都回过了。往上滚或往下滚加载更多，或把「评论区到底自动下滑」打开。

**模型报 400**
部分服务商不接受 `temperature` / `max_tokens`，`background.js` 里已经做了一次降级重试；仍然失败就检查模型名是否拼错。
